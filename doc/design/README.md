# mr.data 设计文档

设计细节的唯一权威层：`project_object.md` 是目标层，`database-design.md` 是表结构层，本篇目录是机制与契约层。用法：按 [00-index.md](00-index.md) 路由表定位到「篇名#节号」，只取该节阅读。

本文件是这套文档的**维护规则**，修改 `doc/design/` 下任何内容前必读。

## 一、对文档的整体要求（每篇、每节都必须满足）

1. **篇头「文档地图」**：≤5 行，每节一行说明，节号与正文标题一致。
2. **每节自包含**：开头一句话说本节回答什么；依赖的前置概念就地一句话复述，不假设读者读过其他节。
3. **章节编号稳定**：`篇名#节号` 即全局唯一地址；新增节追加新编号，**禁止重整旧编号**（外部引用会断）。
4. **文末「证据区」**：列出 `[记录]` 断言的证据（改进号/commit/文档），并说明每条 `[推断]` 的推断路径。
5. **文件名即主题**；`00`/`01` 数字前缀固定给索引与鸟瞰。

## 二、写作规则（硬约束）

1. 写「什么、为什么、边界」，不写「怎么逐行实现」。禁大段抄代码；唯二例外：短函数签名与 **id 派生公式**（公式本身就是契约）。
2. **禁止行号引用**（行号即漂移）。代码引用格式统一 `模块.函数`，需精确定位时附加 commit hash 或改进号。
4. **代码与设计意图冲突时**：记入 [qa-pending.md](qa-pending.md) 问用户裁决，**绝不默默以代码为准**（代码可能有 bug，文档也可能过时——冲突即提问）。
5. **「现状≠设计」的点显式标注**，指向 need_improve.md / last_time_left.md 对应条目，不粉饰。
6. **只写确定性内容**：文档指导开发 agent，收录「还没决定要做」的思路会导致 agent 擅自实现用户没要求的东西。过滤器：**「它现在是真的吗？」** 未决方向与任务唯一存放在 `need_improve.md` 未来增强清单；从清单项只能反推**现行约束**（如「无定时调度、单写者无锁」）写入文档。
7. 文档是代码的上位参照系，不是代码的影子：读完应能知道**该写什么代码、为什么这么写**，无需读过现有代码。

## 三、维护协议

- **改代码动了设计契约**（状态 key、id 派生、降级方向、维度规则、source_type 值域）时，同步更新对应节；改完自查 00-index 路由仍指向正确章节。
- **新决策**：写入 [decisions.md](decisions.md)（D 编号延续改进号序列，格式见文件内样例）。
- **新专有名词/type 值**：登记 [02-glossary.md](02-glossary.md)（一句话定义 + 权威细节指针）；各篇就地复述但不重复造定义。
- **需用户裁决时**：问题按模板写入 [qa-pending.md](qa-pending.md)，用户直接在文档内答复；禁止边写边问、禁止默认代答。
- 每篇文档头部已带断言标注约定说明行，新篇必须保留。
