# 测试编写指导原则（借鉴主流 AI 项目实践）

> 来源：2026-11 对 LangChain 官方测试文档、vLLM 贡献政策、LayerLens/Kanopy 等 LLM 测试实践综述、AI 生成代码维护性实证研究（arXiv 2605.06464），以及 agentic coding 工作流（Anthropic、AGENTS.md 惯例）的调查整理。
> 定位：测试编写的取舍依据。项目无关、长期有效——不写具体功能的对照记录，功能级验收交给各功能的计划文档与人工评审。

## 1. 行业分层模型

主流 AI 项目（LangChain 文档为范式代表）把测试分三层，各层工具不同：

| 层 | 测什么 | 断言形态 | 运行时机 |
|---|---|---|---|
| 单元测试 | 确定性逻辑小块（解析、状态机、prompt 组装、落库行为） | 精确断言，内存假件隔离 | 每次提交 |
| 集成测试 | 真实 API/数据库协作、凭证与 schema 对齐、时延 | 行为与状态断言 | 每次提交或定时 |
| evals | LLM 输出质量（相关性、格式、groundedness） | 规则/评分器/rubric，而非精确字符串 | 改了 prompt/管道才触发（tiered CI） |

关键原则：**LLM 进入调用链之后，精确字符串断言就是错的工具**。断言强度必须匹配契约的稳定性。

## 2. 核心指导原则

### 2.1 文案不是契约，行为才是

业界最常被引用的教训（LayerLens）：给提示语写精确字符串断言，模型/代码换个措辞测试就红；放松成子串匹配，再变又红；最后测试被注释掉——**锁定易变的东西既制造维护成本，又导致测试被删，等于双重浪费**。

推论：交互提示语、日志措辞、错误消息文案属于易变面。可以锁的是：
- 状态变化：标志位、计数清零、行删除、外部存储无悬挂数据；
- 流程语义：放弃、幂等、双重确认、错误后流程不中断；
- 机器消费的格式：审计日志、API 响应、序列化结构——属稳定契约，应精确锁定并与文档样例对齐。

措辞类断言每个命令/界面至多留一个，且优先保留安全关键的（如「此操作不可恢复」）。文案本身的回归保护靠设计文档对照人工验收，不靠测试逐字锁定。

### 2.2 测「留下了什么」，不测「中间长什么样」

检查系统的最终状态与轨迹（LangChain evals 指南），不对中间步骤的呈现格式过度断言。

### 2.3 测试是代码，低价值测试是负资产

- vLLM 贡献政策明文禁止「低价值忙碌工作提交」，要求人对每行负责；
- 实证研究（arXiv 2605.06464）：AI 初始 PR 附带的测试「经常不足且评审后频繁返工」，约 1/10 的生成方法最终在评审中删除——审查与维护认知负担是真实成本；
- 推论：测试数量不追求分支全覆盖，追求「回归时能拦住」。每个测试要能回答「它拦住什么 bug」。

### 2.4 套件要快，CI 分层

多数提交只跑确定性测试（目标 2 分钟内）；只有改动 prompt/管道/eval 相关代码才触发重的套件。慢套件会被绕开，等于没有。

### 2.5 回归用例优先

从真实 bug 出发补测试，而不是从「还能想到什么分支」出发扩充。

## 3. AI 驱动开发下的测试工作流

AI 写测试已成常态（2026 年多数团队的测试由 agent 生成或辅助生成），测试的角色随之变化：它不只是回归网，更是 **agent 的迭代目标**。相应的工作流与质检：

### 3.1 测试先行、红绿迭代

主流 agentic coding 实践（Anthropic）推荐的 TDD 变体：

1. 先让 agent 按期望的输入/输出对写测试，并**显式确认它们失败**（此时禁止写实现）；
2. 对测试满意后**提交并冻结**——后续 agent 写实现时**不许修改测试**；
3. agent 迭代实现直到全绿；
4. 用独立视角（另一 agent 或人）验证实现没有**过拟合测试**。

关键机制是冻结：没有它，agent 遇到红灯时倾向改测试迎合实现，测试就退化为橡皮图章。

### 3.2 AI 生成测试的质检清单

AI 生成测试的典型失败模式与对策：

- **弱断言**：断言「元素存在/页面加载」而非业务结果。对策：断言测**结果**不测**过程**——「删除后表里无此行」，而非「输出了删除提示」。
- **执行顺序依赖**：测试 B 假设测试 A 建了数据，单独跑就挂——最常见的生成失败模式。对策：每个测试自建数据、自清理，可乱序、可单跑。
- **风格漂移**：生成的测试不遵守团队惯例。对策：生成 prompt 里放 3-5 个既有测试作样例，让风格从样例学，不从泛泛的「最佳实践」猜。
- **重复与幻觉**：相近功能的用例重叠膨胀；或测了需求里不存在的功能。对策：提交前查重；每个用例对照需求验收，答不出「拦住什么 bug」的删。

### 3.3 质量门从读 diff 移到验证行为

当代码生成速度超过人工评审容量，评审方式必须改变：从逐行读 diff 转为「测试全绿 + 行为断言覆盖关键路径」的行为验证。这反过来要求测试本身质量过关（3.2），否则门形同虚设。
